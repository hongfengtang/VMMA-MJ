## 1. 部署准备

由授权维护人员确认 Java 8、图形桌面、中控服务地址与终端编号、当前终端所连接药柜的 TCP 地址和端口、现场账号权限，以及运行目录的读写权限。

### 1.1 角色和环境交接

以下是部署职责建议，不表示客户端已经实现这些角色的本地权限隔离。

| 交接方 | 应交付／核对 | 交付方式与边界 |
| --- | --- | --- |
| 医院业务负责人／药师 | 适用业务、药袋核对规范、实物对账、交班及异常升级 SOP | 明确哪些操作可以继续、哪些必须暂停；不以界面绿底替代药品核对 |
| 中控管理员 | 终端登记、批准的基础 URL、员工授权、待取计划与回写对账渠道 | 通过院方受控渠道交接，不把真实账号、token、患者资料写入文档 |
| 设备维护人员 | 已验收的单设备地址／端口、设备就绪检查与清障 SOP | 软件仅提供 TCP 客户端接线；多端口记录不是多柜隔离方案 |
| Windows／部署维护人员 | JDK 8 路径与位数、运行目录、快捷方式工作目录、日志权限、发布校验值 | 使用医院批准的安装包和授权；不要为排障关闭防火墙或安全软件 |
| 发布负责人 | 包名、源码版本、构建参数、依赖及工具授权、回退包、验收记录 | 测试包能构建不等于已经批准生产；混淆 DEMO 包不得用于商业生产 |

上线前保留一份受控交接单：终端标识、设备方案、JDK 版本、JAR 校验值、配置备份位置、当班联系人和停机窗口。真实地址及身份信息只放在受控交接单，不放进公开手册。

### 1.2 Windows 11 的 Java 8 准备

1. 由维护人员安装医院批准且授权适用的 **JDK 8**；通常采用与 Windows 11 终端匹配的 x64 包，不要只安装无编译器的 JRE。
2. 记录实际安装目录。以下 PowerShell 的 `C:\Java\jdk8` 是示例，必须替换；修改只影响当前终端窗口，不改系统环境或其他应用。
3. 在图形桌面会话操作，先确认输入设备、中文字体及显示缩放；本程序不是可直接作为无桌面服务运行的 Web 应用。
4. 核对显式 JDK 命令和 `PATH` 解析结果，避免机器同时安装新版 Java 时用错。

```powershell
$env:JAVA_HOME = 'C:\Java\jdk8'
$env:Path = "$env:JAVA_HOME\bin;$env:Path"
& "$env:JAVA_HOME\bin\java.exe" -version
& "$env:JAVA_HOME\bin\javac.exe" -version
where.exe java
```

`java` 和 `javac` 应显示 `1.8...`。若路径不存在或显示新版，先修正环境再构建／启动，不要通过降低安全限制或换用随机 JDK 解决。

源码使用 `sun.misc.BASE64Encoder/BASE64Decoder`，不能仅因 Maven 指定 Java 8 目标就认为 JDK 11/17/21 也能直接编译。生产终端应使用经部署方确认的 Java 8 环境。

### 1.3 完整运行目录

部署目录至少包含经批准的可执行 JAR、`data/system.db` 和完整 `images/`。`logs/` 需要可写；`lib/` 的 Allatori 是构建依赖，不是启动 JAR 的必需外部目录。

```text
<运行目录>/
├── MMH-VMMA-1.0.jar
├── data/system.db
├── images/
├── logs/
└── application.yaml  # 可选：经部署方批准的外部配置
```

这些路径按进程工作目录解析，不按 JAR 所在目录自动解析。启动前必须切到运行目录。首次部署使用经批准的配置库，不要复制其他终端的配置后直接连接真实设备。

当前普通 Boot JAR 不包含运行用的 `data/system.db` 和外部 `images/`；UI 使用相对文件路径加载 `images/account.png`、`check.png`、`back.png`、`nopic.png` 等。应单独交付本终端配置库和完整 `images/`，不要只交付 JAR 或只补一个缺失图标。数据库父目录和日志目录须由维护人员批准并准备好。

## 2. 构建、启动与停止

### 2.1 从源码构建

仅开发／发布维护人员需要构建，普通操作人员使用已验收发布包。Windows PowerShell 切到源码根目录后执行：

```powershell
Set-Location 'C:\VMMA-MJ'
$env:JAVA_HOME = 'C:\Java\jdk8'
$env:Path = "$env:JAVA_HOME\bin;$env:Path"
.\mvnw.cmd -v
.\mvnw.cmd -Dexec.skip=true package
```

本次核对的 Mac 默认 Java 是 26，已有 Java 8 的明确路径为 `/Library/Java/JavaVirtualMachines/jdk-1.8.jdk/Contents/Home`。在源码根目录的新 shell 中显式选择它：

```bash
export JAVA_HOME='/Library/Java/JavaVirtualMachines/jdk-1.8.jdk/Contents/Home'
export PATH="$JAVA_HOME/bin:$PATH"
"$JAVA_HOME/bin/java" -version
"$JAVA_HOME/bin/javac" -version
bash ./mvnw -v
bash ./mvnw -Dexec.skip=true package
```

此 Mac Java 8 为 x86_64；其他 Mac 的安装路径及 Apple Silicon 兼容运行环境需另行确认，不能直接假定默认 Java 可用。该命令跳过 Allatori 外部执行步骤，默认跳过测试是现有 POM 设置，不能将 `package` 成功写成测试全部通过。首次构建的依赖获取由维护网络策略管理。

IDEA 导入 `pom.xml`，Project SDK 与 Maven Runner 使用 JDK 8，启用 Lombok 所需注解处理。运行类为 `com.mmh.vmma.VmmaApplication`，Working directory 设为项目根目录；不要用空上下文测试代替桌面启动入口。

### 2.2 发布包选择：不要只看文件大小

下表依据此前本机构建及现有产物的静态包结构核验；未在 Windows 11 现场运行，大小为近似值，不能代替版本和 SHA-256 检查。

| 产物 | 结构／入口 | 使用结论 |
| --- | --- | --- |
| `target/MMH-VMMA-1.0.jar`，约 42 MB | Boot `JarLauncher` 为 `Main-Class`，`VmmaApplication` 为 `Start-Class`；应用类在 `BOOT-INF/classes` | 本次核验的可执行包候选；经发布批准后使用 `java -jar` |
| `target/MMH-VMMA-1.0-jar-with-dependencies.jar`，约 80 MB | Manifest 指向应用主类，但应用仍在 `BOOT-INF/classes`，没有根目录主类 | 本次产物不能直接按 `java -jar` 正常定位主类；不推荐部署 |
| `.jar.original` 或其他未验收产物 | 不能仅凭后缀判断依赖和启动结构 | 不作为操作人员的启动包 |
| Allatori 混淆输出 | 本地工具为 **Allatori 7.9 DEMO / NOT FOR COMMERCIAL USE** | 当前 DEMO 工具／输出不得作为商业生产发布方案 |

现有 Boot 包含 56 个嵌套依赖，SQLite JDBC `3.32.3.3` 包含 Windows x86／x86_64 原生 DLL；静态核验应用字节码为 52（Java 8），非多版本目录类没有高于 52 的版本。无需操作人员额外下载随机 SQLite DLL；位数、驱动原生库加载、系统临时目录权限仍需在目标 Windows 终端验收。上述结构证据不等于已经通过 Windows 11 运行或新版 JDK 源码兼容验证。

正式混淆发布另需有效工具授权、打包结构验证与现场验收；参见[项目首页](../README.md)。`lib/allatori.jar` 本地存在但不受 Git 跟踪，不应假定新检出仓库自动拥有它。

### 2.3 启动

Windows PowerShell 使用显式 Java 8 路径，在部署目录执行；路径仍为示例：

```powershell
Set-Location 'C:\VMMA-MJ'
$env:JAVA_HOME = 'C:\Java\jdk8'
Get-FileHash .\MMH-VMMA-1.0.jar -Algorithm SHA256
& "$env:JAVA_HOME\bin\java.exe" -jar .\MMH-VMMA-1.0.jar
```

启动前将校验值与发布交接单比对。首次验收建议保留控制台，便于看到启动失败；不要先用 `javaw.exe` 隐藏错误。Windows 快捷方式的「起始位置」也必须是运行目录，不能只设置 JAR 的绝对路径。

Mac 已按上节选择 Java 8 后，在部署目录执行：

```bash
"$JAVA_HOME/bin/java" -jar ./MMH-VMMA-1.0.jar
```

若使用源码根目录和 `target/` 的 Boot 包，只把 JAR 参数改为 `target/MMH-VMMA-1.0.jar`（Windows 为 `.\target\MMH-VMMA-1.0.jar`），工作目录仍是根目录。不要双击 JAR 猜测启动环境，不要在设备正在调剂时另启第二个实例。

外部 YAML 可通过 `--spring.config.additional-location=file:./application.yaml` 加载；文件需要部署方提供。数据库/日志可按 Spring Boot 配置规则覆盖，终端和药柜网络参数则由本地配置表管理。

### 2.4 停止与重启的前提

停止前确认没有调剂进行中，已核对设备取货状态和中控结果，且操作人员已登出。使用授权的应用退出流程；界面无响应时由维护人员按现场规程处理，不能靠重启判断上一笔出药是否成功。

变更药柜或中控配置后，在完成上述核对的前提下重启应用，使初始化流程重新读取参数并建立连接。

## 3. 配置库、备份与升级

`data/system.db` 的配置表为 `t_system_config`，存放 `cabinet` 和 `control_center` 两项 JSON BLOB。它不是本地药品库存库，不要直接编辑 BLOB，也不要执行旧版清理脚本来修复新版本异常。

默认日志为 `logs/vmma.log`，按 YAML 配置滚动。DEBUG/TRACE 或错误日志可能记录请求、身份或业务内容；故障材料应先脱敏，并保留受控原件用于现场追溯。

日志 UTF-8 配置只说明日志输出编码，不能据此认定数据库 JSON BLOB 使用同一编码。现有数据库字符集应在部署与升级时保持兼容；Windows 启动不应无条件增加 `-Dfile.encoding=UTF-8`，字符显示异常先交维护人员核对原库编码与运行环境，不自动转码或重写配置。

由维护人员执行升级时：

1. 停止受影响终端的业务，核对最后一笔调剂的实物、设备与中控记录。
2. 按正常流程退出，备份原发布 JAR、外部 YAML、完整 `images/`、`data/system.db` 和必要日志；若存在 SQLite 的 `-wal/-shm` 文件，采用一致性备份方式，不能只复制活跃主库。
3. 记录版本和配置摘要，替换经批准的新包；不要用源码仓库的配置库覆盖现场配置。
4. 从正确工作目录启动，检查初始化、登录和查询；设备动作验证只在批准的测试条件下进行。
5. 如需回退，先停止并核对新版本是否已产生业务动作，再恢复兼容的程序/配置；恢复本地文件不会回滚中控库存或实物出药。

备份至少应记录以下内容，按医院权限控制保管，不上传未经脱敏的数据库或日志：

| 项目 | 备份／回退要求 |
| --- | --- |
| 旧 JAR、版本、SHA-256 | 保留原包，不仅记录新包；区分 Boot 包与 Assembly 包 |
| 外部 YAML、`data/`、`images/` | 使用停机后完整且一致的备份；存在伴随文件时由维护人员确认一致性 |
| 日志及最后一笔对账状态 | 保留时间范围与处理结论，不能只备份本地配置而遗漏未决业务 |
| JDK、启动命令、工作目录 | 记录真实部署环境；回退时避免仍启动错误目录的新包 |

只有在批准停机且确认进程已结束后才复制／替换运行文件；本手册不提供活跃数据库热复制命令。回退时先回答：新版本是否已经出药？是否有待回写／争议记录？旧版本是否兼容当前中控与配置？未确认前交授权人员处理，不自动恢复整目录覆盖现场。

<a id="configuration"></a>
## 4. 首次初始化与系统参数

启动先显示「正在初始化，請稍後……」，读取本地配置、连接设备、调用中控注册。正常情况下进入「請輸入員工編號」登录页。

### 4.1 启动阶段与屏幕识别

| 阶段／可能提示 | 正在处理 | 操作人员应做什么 |
| --- | --- | --- |
| 「正在初始化，請稍後……」 | 居中小进度窗口，约 350×80 | 等待，勿再次启动；记录长期停留的最后提示 |
| 「讀取藥品櫃配置數據……」／中央控管配置 | 读取本地两项配置 | 缺失／解析异常交维护人员检查目录和配置，不自行建业务表 |
| 「正在連接Signage......」 | 使用配置中的设备 TCP 客户端地址 | 本地 `CONNECTING` 等待约 60 秒；不是固定完整启动期限 |
| 「連接Signage成功！」 | 连接等待结束的 UI 提示 | 不能仅凭此文字认定设备允许出货 |
| 中控注册／「系統啟動成功！」 | `/system/init` 注册终端，保存系统 token | 没有独立用户登录；进度成功不替代中控／设备验收 |
| 「請輸入員工編號」 | 登录页 | 核对现场终端后再登录 |
| 「--請設置連接端口訊息--」 | 初始化失败结果对应配置页 | 仅授权人员按照下节维护；并非所有启动异常都能自动到达此页 |

主窗口实际固定 **1280×800**、居中、无边框且不可调整大小，不是真正自适应全屏。登录页顶部右角为无文字退出位置，中间是编号框／「確認」，下半部是软键盘；没有正常可达的最小化菜单或可见倒计时。Windows 分辨率、显示缩放及远程桌面切换须现场验收，遮挡时不要凭坐标盲点。

缺少柜体或中控配置等初始化失败结果会使主窗口转配置页。**正常登录后的界面没有可达的管理按钮**；不要尝试通过删除配置、破坏网络或使用源码内置口令强行进入配置。配置页没有管理员密码输入或口令发放功能；角色与维护授权由院方交接，不等于客户端有本地权限检查。

### 4.2 参数完整表

JSON 属性用于维护人员理解保存归属，不是要求操作人员直接改库；精确字段结构见[详细设计](DETAILED_DESIGN.md)。

| 界面名称 | 保存属性 | 默认／选择项 | 实际校验与使用限制 |
| --- | --- | --- | --- |
| `*用戶名稱` | `cabinet.customer` | 无配置时空 | 必填；这是客户名称，不是员工账号；保存原始文本 |
| `*終端編號` | `cabinet.terminalid` | 无配置时空 | 必填，与中控登记一致；保存原始文本 |
| `端口類型` | `portModes[].mode` | 默认 `TCP/UDP`；另有串口 | 名称不表示 UDP 已实现；当前选择 TCP Client |
| `新增端口` | 决定追加／更新 | 默认关闭 | 新增须打开；未选行且关闭时不会增加端口 |
| `連接方式` | `mode` | Client=`1`；Server=`2` | 默认 Client；Server 连接尚未实现 |
| `服務IP` | `address` | 重置 `127.0.0.1` | 新增 Client 检查非空；格式提示不保证阻止保存；Server 模式禁用 |
| `連接端口` | `portNumber`，字符串 | 重置 `20000` | 键入仅数字，未完整验证 `1–65535`；已有端口更新检查更弱 |
| `串口編號` | `name` | COM1～COM9，另含 TCP/UDP；默认 COM1 | 串口连接尚未实现，不用于本版生产接线 |
| `波特率` | `baudRate` | 9600／19200／38400／57600／115200；默认9600 | 串口参数，列表选择 |
| `數據位` | `dataBites` | 5／6／7／8；默认5 | 字段拼写按源码保留 |
| `校驗位` | `parity` | None／Even／Odd／Mark／Space；默认None | 串口参数，列表选择 |
| `停止位` | `stopBits` | 1／1.5／2；默认1 | 起始位控件已注释，`startBits` 保存为空 |
| `流  控` | `flowControl` | None／RTS/CTS／XON/XOFF；默认None | 串口参数，列表选择 |
| `*中央控管URL` | `control_center.address` | 无配置时空 | 必填，可解析 URI 且 host 非空；未强制 HTTP(S) 或测试连通 |

`server.type`、`server.title`、数据库和日志设置属于应用 YAML，不在此页保存；此页也不保存用户密码或 token。TCP 模式会将串口属性置空，串口模式会将网络属性置空。默认 IP／端口仅为重置值，禁止照抄成现场地址。

### 4.3 保存、删除与生效

已由批准的维护流程进入配置页后：

1. 填写 `*用戶名稱`，这是终端显示的客户名称，不是员工登录账号。
2. 填写 `*終端編號` 和 `*中央控管URL`，必须与中控登记及现场分配一致。
3. 首次增加设备连接时打开「新增端口」，选择 `TCP/UDP` 和 `TCP/UDP Client`，填写维护人员提供的「服務IP」「連接端口」。
4. 按「保存」，核对终端、中控和端口记录。没有明确整体成功弹窗；如出现错误，须重新检查两份配置是否均已保存。
5. 初始化失败路径按「退出」会提示「配置修改保存后，請重啟系統!」并结束应用；从正确工作目录重新启动。

当前实际支持的是 TCP Client，不是 UDP、串口或 TCP Server。默认 `127.0.0.1:20000` 只是重置值，不能照抄为现场药柜地址；配置多条端口也不代表具备多柜独立连接能力，当前应按已验收的单设备连接方案部署。

修改已有端口先选择记录，关闭新增开关后「保存」更新；「刪除」须选行并确认。**不要在表格排序后直接更新/删除**，当前视图索引处理存在风险。保存前由维护人员自行检查 IPv4、合法端口范围和 HTTP(S) URL，不能完全依赖界面验证。

保存只写本地数据库，不热更新当前连接和全局参数；成功初始化后从配置页「退出」也不是可靠的返回菜单路径。后续配置变更应在暂停业务并完成对账后，按现场批准的维护流程退出、修改并重启。

保存先落库 `cabinet`，再验证并保存 `control_center`，不是整体原子提交；出现 URL 错误时，柜体项可能已经保存。必填验证只用修剪后值判断，客户／终端保存值仍可能带空格。IPv4 键入过滤对含零段、光标替换处理有限，勿用反复试输代替维护核验。

配置窗口尺寸变化会重读数据库并重置端口输入；修改期间避免切换显示设置。删除前确认所选端口和终端，取消删除并不执行重启；从表格排序后的视图直接操作存在索引风险。

## 5. 登录、登出与软键盘

输入由医院授权的员工编号，按 Enter 或「確認」。中控认可后直接进入调剂页；红色提示显示中控拒绝原因时，应核对编号或联系维护人员。

点击编号框确认焦点后输入，不增加前后空格；失败时输入可能被全选，再次输入会替换它。空编号按 Enter 只返回输入框；按「確認」则经过登录函数并可能显示「用戶名不能為空」。成功进入调剂后核对顶部显示的员工身份，不借用上一班已登录会话。

本版没有账号密码输入步骤，不提供密码修改、人脸、指纹或独立刷卡采集。键盘模拟输入设备可以向文本框输入字符，但其安装方式与自动 Enter 行为需现场确认。

登录页软键盘通过 AWT Robot 向当前焦点发送系统按键；先确保员工编号框有焦点。「Delete」实际为退格，Shift 是切换式状态，使用后注意关闭，避免影响后续条码输入。图形桌面和系统键盘权限需现场配置。

调剂页页头「退出」是**登出**，会回登录页，程序继续运行。工作结束或离开终端必须主动登出；不能依赖自动闲置登出，本版没有执行该计时逻辑。

确需结束程序时，先完成调剂与对账、登出，再使用登录页右上角无文字退出按钮；鼠标移入会显示退出图标。它结束进程，与调剂页「退出」不同。

## 6. 双条码调剂

### 6.0 页面位置示意

```text
┌────────────────── 调剂主窗口：1280×800，居中 ───────────────┐
│ 员工身份                                                │
│                  调剂／扫码提示                  [退出] │
│ 藥袋下方條碼： [文本框1]                                │
│ 藥袋上方條碼： [文本框2]                                │
│ [即時藥存量]             [清除]                  [確認] │
│ 藥品補藥提示列表：药物编号／药名／警示量／现存总量        │
│                               |<< < > >>| 页码 /页 Go │
└─────────────────────────────────────────────────────────┘
```

这是相对位置图，不含患者或账号示例。调剂对话框约 800×800：左侧图片、右上药品信息、右下患者／处方信息、下方结果提示和右下「確定」。它是模态窗口，不能同时操作背后的调剂页。

### 6.1 输入与开始

**开始前按医院规程核对药袋、条码归属和终端。按「確認」或在上方条码框按 Enter 后，系统会查询计划并自动出药，没有第二次出药前确认。**

1. 在「藥袋下方條碼」输入或扫描药袋下方条码。
2. 按 Enter，把焦点移到「藥袋上方條碼」。
3. 输入或扫描同一药袋的上方条码。
4. 核对两个输入正确后，按 Enter 或「確認」开始。输错且尚未开始时按「清除」重新输入。
5. 读取失败或「沒有待取藥物列表」时，先核对两段输入和中控计划，不要连续提交。

扫描枪是否自动发送 Enter、药袋版式及硬件驱动不在源码定义范围。因为上方 Enter 就会启动，请在第一次使用前由维护人员确认扫描行为。

| 路径 | 安全操作顺序 | 代码实际行为 |
| --- | --- | --- |
| 扫描／Enter 路径 | 点下方框→扫描下方→Enter→扫描上方→最终 Enter | 下方 Enter 清空上方并转焦点；上方非空 Enter 直接查询，并未重新逐项检查下方 |
| 手工／按钮路径 | 按标签分别填写两框，暂不按最终 Enter→核对→点「確認」一次 | 按钮分别检查两框非空，缺失时弹「請輸入藥品條碼！」并聚焦对应框 |
| 尚未提交时修正 | 点「清除」→重新输入同一药袋的两段 | 清空两框并聚焦下方；重新在下方按 Enter 会清除上方原值 |

文本框获得焦点会全选已有内容，扫描可覆盖原值；提示文字只能帮助辨认当前框，不代替核对。客户端没有条码长度、格式、校验位或同袋关联校验，空格也不能视为有效条码。页面切换后输入被清空，返回调剂必须重新核对两框。

### 6.1.1 扫码后弹「登录超时」：先识别发生阶段

若现场扫码查询后弹出「登录超时／登入超時」等文字，本页在 `/user/provide/query` 返回非成功业务结果时直接将 **中控响应 `message`** 放进「錯誤」弹窗；它不是扫码框内置的固定超时文案。弹窗关闭后，页头可能改成「讀取取藥訊息錯誤」，失去原始详细文字。

1. 暂停再次提交，记录弹窗原文、时间、是否已经打开过自动出药窗口；按医院要求脱敏。
2. 如已出药、存在上一单未决任务或无法判断，按[异常处理](#troubleshooting)交授权人员对账，不重扫整单。
3. 只有确认没有未决设备动作且按医院流程允许重新查询时，关闭提示，点调剂页「退出」回登录。
4. 重新输入本人授权员工编号，完成中控登录；新登录响应中的用户 token 会替换旧会话。回调剂后重新输入同袋双条码，按批准流程提交一次。
5. 若仍失败，交中控管理员核查该请求的业务结果和会话状态；操作人员不要手工改 token、配置或处方。

**本地没有 45 秒倒计时、token 自动续期或超时自动跳回登录逻辑。** 初始化系统 token 与员工用户 token 不同，扫码／结果回写取当前用户 token。没有现场原始响应和服务端记录时，不能确认根因一定是 token 到期、失效规则是什么或有效时长是多少；重新登录也是受控恢复步骤，不是根因证明。

### 6.2 自动执行期间

有计划时打开「調劑操作確認」，显示药品、单位、储位、计划量与库存、批号/效期、患者及处方相关字段。窗口显示后自动执行，「確定」先禁用，不是出药前批准按钮。

等待设备与界面反馈，不重复扫描、不另起实例，也不要通过关闭程序中止设备动作。界面没有可靠的整单取消按钮；某个储位失败后，其他已排队任务仍可能继续。

「正在取第 N 包」是尝试进度，不是成功确认。多药品图片可能仍显示首项，核对时应结合文本字段、处方及院方规程，不能单凭图片。

如显示计划量大于库存、出货失败或其他异常，立即通知授权人员按现场规程处理；当前客户端库存提示并非可靠硬阻断，不能以提示出现就认定设备没有动作。

### 6.3 完成与对账

全部储位有终结反馈后，窗口启用「確定」并尝试回传中控。核对设备反馈、界面异常、中控记录和实物，再按「確定」关闭，返回调剂页后可处理下一笔。回写使用查询响应中的条码／处方标识及逐药品、逐储位的数量和状态，不是操作人员手工输入的盘点结果。

**「確定」可点击不等于回写成功；最后一项成功提示也不等于整单所有储位都成功。** 网络或回写异常时，本版没有可靠的回写重试按钮或持久化补传。

失败储位上报的数量仅代表此前按当前软件规则（含下述定制分支）判定完成的包数；超时当前包仍可能已经出药。必须由授权人员核对并处置，不能重扫整单“补取”，也不能用重启或恢复本地数据库回滚结果。

当前保留客户新设备定制：出货等待阶段累计收到三次当前状态 `0x02`（不要求连续）时，程序可将当前包判为成功，不必同时取得完整五项完成条件。回调没有区分常规／定制成功的标记，UI 与回写结果无法据此区分路径。**程序成功不等于该定制分支拥有全部硬件完成证据**；实物数量、设备状态及后台记账仍依医院 SOP 对账。此规则不是重试操作，也不是参数页可配置开关；操作人员不调整此判定或发送原始控制报文。

## 7. 告警、库存与药品详情

### 7.1 调剂页补药提示

调剂页显示中控 `isAlarm` 标记的药物编号、药名、警示量和现存总量。告警行用于提醒维护/补药人员，不是本页执行补药的入口。

该列表在调剂页重新显示时查询，不是实时持续采样。使用翻页按钮查看更多记录；若用页码框和 `Go`，只输入显示范围内的有效正整数。

### 7.2 即时药存量

1. 调剂页按「即時藥存量」。
2. 查看储位号、药名、现存总药量、储位现存量、最大量、药物编号。
3. 使用 `|<<`、`<`、`>`、`>>|` 翻页，或输入有效页码后按 `Go`。
4. 选择需要查看的储位行，按「詳情」。
5. 查看只读药品/单位/包装/管制类型、所选储位的现存量和最大量、图片及告警提示。
6. 详情「返回」关闭；库存页「返回」回调剂。

同一药品有多个储位时分行显示，药品总量会重复；不要把这些重复总量相加。告警主要是药品级标记；排序后颜色可能错位，不能只依据颜色判断某个储位是否不足。

「即時」表示从中控读取；进入页面才重新查询，翻页和详情返回通常使用内存结果。药品学名等字段可能没有填充，部分接口字段没有详情控件。

搜索栏和「批次取藥」入口当前隐藏，不列为可执行操作。本页和详情没有编辑库存、确认补药、开门、盘点或退药功能。

详情「返回」在窗口右下，库存「返回」「詳情」在页面底部右侧，两者用途不同。灰色「詳情」表示未选择行，先单击目标储位再查看；表格不能直接编辑。回到调剂页会重新查询告警并清空条码，不保留上一袋输入。

## 8. 常见异常处理

| 情况 / 提示 | 处理与边界 |
| --- | --- |
| 启动时报找不到 `VmmaApplication` 主类 | 核对是否误选 Assembly 包；换回已批准的 Boot 可执行包，不随机拼接 classpath |
| Java 版本、`sun.misc` 类或原生库加载错误 | 核对 JDK 8、进程位数、包和完整异常；不同错误不是同一根因，不随意下载 DLL |
| 缺少柜体或中控配置 | 授权维护人员检查配置库，完成配置后重启；勿执行旧业务建表脚本 |
| 初始化长期停留 / 失败 | 检查工作目录、数据库/JSON、地址端口和日志；显示启动成功也不能代替设备就绪确认 |
| 登录拒绝 | 按中控消息核对员工编号/授权；请求异常联系中控维护 |
| 扫码查询弹「登录超时／登入超時」 | 按[分阶段处理](#dispensing)确认无未决出药后重新登录；中控消息不能单独证明固定 token 时长 |
| 「讀取取藥訊息錯誤」 | 核对双条码和中控服务，确认是否进入过出药窗口再决定后续处置 |
| 「沒有待取藥物列表」 | 核对中控待取计划及历史结果，勿自行改处方或库存 |
| 「藥品櫃當前狀態為不可出貨狀態」 | 不继续提交新任务，由设备维护人员依厂商规程确认状态 |
| 「查詢販賣機狀態無迴應」 | 检查授权网络端点/设备连接；不是完整厂商故障诊断 |
| 「設置退幣動作無迴應」 / 「設置取貨動作無迴應」 | 准备阶段缺少所需确认/事件，联系设备维护与系统管理员 |
| 「取貨動作無迴應」 / 出货失败 | 当前包可能已经落药，必须核对实物与中控，禁止盲目重取 |
| 「系統執行命令報錯」 / 「無法識別返回碼」 | 记录时间、储位和已完成数量，由维护人员排查，不假设会自动重试 |
| 结果回写失败 / 提示联系管理员 | 物理动作与后台记账可能不一致，没有自动补传；按授权对账流程处理 |
| 对话框一直无法按「確定」 | 无独立自动取消/恢复按钮；不要强制把本单当失败，交维护人员处理 |
| 告警库存或详情缺值 | 通知维护人员核对中控数据；本客户端不能完成补药或库存修正 |

出货阶段的 30 秒是等待进展阈值，不是全单硬期限。CONNECTED 只表示连接层状态，不保证允许出货。维护人员收集故障时间、终端/储位标识、界面消息、中控处理结果和必要日志，全部材料按医院要求脱敏。

设备急停、开柜、清障、断电、补药和安全门处理由厂商及医院 SOP 规定，本手册不提供绕过互锁、原始报文控制或直接改库的恢复方法。

### 8.1 先分层，后处理

1. **进程尚未启动／无窗口**：检查正确包、Java 8、工作目录、图形会话和控制台异常；不要把所有情况归为网络故障。
2. **停在初始化**：记录最后一条进度文字，检查配置可读性与已有连接；后台异常可能未能切到配置页。
3. **登录／扫码查询被拒**：保存中控返回消息，由中控人员核对授权、计划和会话；错误码／消息未取到时只记录现象。
4. **已打开出药窗口**：按可能有物理动作处理，不先重启、重扫或终止进程；由业务与设备人员核对实物。
5. **出药反馈结束但回写异常**：按实物与中控账务可能不一致处理；查询库存不能代替逐单对账。

### 8.2 Windows PowerShell 只读检查

以下命令只用于医院批准的本机诊断，不改配置、不停止进程、不主动连接药柜。真实路径、PID、网络端点和日志可能敏感；输出只在授权环境查看，提交材料前脱敏。

先确认当前目录及发布文件，不读取配置库内容：

```powershell
Set-Location 'C:\VMMA-MJ'
Get-Location
Get-Item .\MMH-VMMA-1.0.jar, .\data\system.db |
    Select-Object Name, Length, LastWriteTime
Get-FileHash .\MMH-VMMA-1.0.jar -Algorithm SHA256
Test-Path .\images\account.png
Test-Path .\images\check.png
Test-Path .\images\nopic.png
Get-Command java -All | Select-Object Source
```

不存在文件先核对部署目录；配置库大小和时间戳不能证明 JSON 正确或指向正确终端。此检查也不能验证目录写权限，不通过随意创建文件／改 ACL 探测生产目录。

再识别 Java 进程，避免把其他 Java 应用当成本终端；不输出可能带敏感参数的完整命令行：

```powershell
Get-CimInstance Win32_Process -Filter "Name='java.exe' OR Name='javaw.exe'" |
    Select-Object ProcessId, ExecutablePath, CreationDate
```

由维护人员确认本应用 PID 后，把下例 `1234` 替换为该 PID，只查看已有 TCP 连接：

```powershell
$vmmaProcessId = 1234
Get-NetTCPConnection -OwningProcess $vmmaProcessId |
    Select-Object State, LocalAddress, LocalPort, RemoteAddress, RemotePort
```

没有记录／权限不足不是药柜故障结论；有 Established 也不表示中控授权或设备允许出货。不要清空其他进程连接、结束所有 Java 进程，或为测试连通发送原始药柜报文。

日志默认位置是运行目录下 `logs/vmma.log`，外部 YAML 可覆盖。先看文件时间与滚动文件，再在授权终端查看相关时间段：

```powershell
Get-ChildItem .\logs -File |
    Select-Object Name, Length, LastWriteTime
Get-Content .\logs\vmma.log -Tail 120
```

默认日志配置包含应用 TRACE，可能出现身份、请求／响应和业务字段；`Tail` 不保证涵盖整单。不要清空日志、只截最后成功行，或把整份日志粘贴到公开工单；保留原件，在受控副本中关联故障前后时间。

### 8.3 故障交接最小材料

| 必需材料 | 采集边界 |
| --- | --- |
| 时间、阶段、弹窗原文、是否出现出药窗口 | 截图先遮盖员工、条码与患者信息；弹窗原文和页头通用错误分开记录 |
| 发布版本、JAR SHA-256、JDK 路径／位数、启动工作目录 | 不提供真实口令、token 或内部 URL；错误包须说明产物名称 |
| 当前与此前未决业务的处置状态 | 实物数量由授权人员按 SOP 核对，不能由进度计数反推 |
| 中控查询／回写结果、设备维护结论、相关日志时间段 | 未拿到的证据标为“待核实”，不要写成 token 到期或药柜断线已证实 |

重新登录会替换当前用户会话，重启会丢失内存中的本单状态；这两项都不是自动账务恢复。应在完成阶段识别与授权对账后决定是否恢复操作。

<a id="unsupported"></a>
## 9. 本版不适用的操作

不要沿用历史 README 中“选病床/医嘱”“QRCode 临时取药”“紧急取药”的步骤。当前常规界面是双条码调剂；批次入口隐藏，功能菜单未接线，退药、补药、盘点和自动闲置登出没有完整执行流程。

底层类、菜单常量、图片或 `application-return.yaml` 的存在不能证明上述操作已可用。需要新增这些功能时必须完成开发、权限与设备/中控联调，不应由操作人员直接开启隐藏入口。

## 10. 现场验收与交班检查表

以下均是需在目标终端执行并签认的验收项，不表示本次源码阅读已完成现场测试。设备动作、超时与异常恢复验证必须使用批准条件和测试数据，不在正常患者业务中故意制造故障。

| 阶段 | 验收／交班项目 | 合格证据 |
| --- | --- | --- |
| 发布准备 | Boot 包、版本、校验值、工具授权与回退包一致 | 发布交接单，不以“JAR 较大”判断正确包 |
| 桌面环境 | Windows 11 的 JDK 8 位数、图形会话、字体／缩放、窗口完整显示 | 环境记录；所有实际按钮可辨认、可操作 |
| 运行目录 | JAR、完整 `images/`、本终端配置库、日志目录、快捷方式起始位置正确 | 维护确认；不覆盖其他终端配置 |
| 初始化 | 记录各阶段，中控终端登记与已验收单设备方案一致 | 中控与设备人员确认；进度成功不是唯一证据 |
| 员工登录 | Enter 与「確認」均使用授权员工流程，页头身份正确，登出可回登录 | 批准测试记录；不公开测试账号 |
| 扫描焦点 | 下方→上方顺序、扫码自动 Enter、重新聚焦全选、清除与按钮路径 | 操作培训记录；首次自动回车行为已确认 |
| 调剂执行 | 自动开始时机、禁用／启用「確定」、字段及异常提示、客户设备判定 | 经批准的设备测试与实物／中控逐单对账 |
